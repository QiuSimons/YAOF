# kix-discipline spec（需求三检契约）

- 记录时间: 2026-10-16T15:19:52.210Z

## Goal（要解决的根本问题）
判定 BRCM fullcone NAT 升级（commit 83487bc + 33410f1，共 5 个补丁：kernel 982/983、libnftnl、nftables、firewall4、luci）的实现质量，并给出在「保留 brcm 期望表设计」前提下减少 CPU 周期/分配/拷贝、且更贴合 RFC 4787 的改进判据。

## XY 检查（需求三检①：要 X 真需要的是 Y？）
用户要 X=「审查升级质量」；真需要 Y=一份能直接指导修改的缺陷清单：哪些是真 bug（会错发/漏发/崩溃/失效）、哪些违背 RFC 4787 必备条款、哪些是可量化的 CPU/alloc/copy 成本点。若只给泛泛评价则无法驱动修复，故必须以「可复核的证据 + 具体失效场景 + 修法」结算。

## 前提假设（需求三检②：前提可验证吗？）
①能被阅读的目标代码 = PATCH/ 下的补丁 + yaof-build-x86_64/openwrt 中已应用的内核 6.12.94 源码/firewall4 制品（已确认补丁确实落盘）；②RFC 4787 UDP 必备条款（REQ-1 endpoint-independent mapping、REQ-4 hairpinning、REQ-6 filtering 行为、4.2.2 端口奇偶）可作为验收基准；③无需在真实路由器上抓包即可定论的部分（逻辑/锁/RCU/生命周期）优先，需设备验证的部分标为未验证。

## 更优路径（需求三检③：有更高维度解法吗？）
不改代码，solo 主线程审查：读补丁 + 读已应用内核源码（nf_nat_masquerade.c / nf_nat_core.c / nf_conntrack_expect.c / ft_flow_offload.c / firewall4 制品）交叉验证；不派子代理，因为问题域集中在 5 个文件、证据可从源码直接闭合，扇出成本高于收益。输出按「真 bug / RFC 差距 / 性能成本」分层，每条附失效场景与修法。

## 验收标准（可验证的完成定义）
每条 finding 有文件名:行号或代码片段作证据，并说明「什么输入 → 什么错误结果」；对无法从源码闭合的点（真实设备上的 nft 探测、offload 行为）显式标注为未验证；最终给出按 ROI 排序的修改清单。

## 执行模式（编曲留痕：成员组合 + 一句理由）
solo：审查 + 源码交叉验证，域窄且证据可闭合，不组队（省扇出开销）

## 行为契约（必须不变 / 必须改变 / 必须成立 / 歧义解读）
必须不变：BRCM 期望表（nf_conntrack_expect）作为 fullcone 外部入站可达性的载体这一设计选择。必须成立：结论须基于已落盘源码而非补丁文本的推测。契约歧义：用户未说明「要不要直接改代码」，故先交付审查结论，修改待确认。
